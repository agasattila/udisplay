## Problem Statement
The `data` characteristic uses NOTIFY, which has no delivery guarantee. A
notification can be dropped by the host stack with nobody noticing, which
corrupts BLE reassembly silently. The MVVM work needs a link where "delivered
or disconnected" holds in both directions, with no new packet-level protocol.

## Premises
1. Confirmed ATT operations in both directions are enough. No packet ACK or
   retransmit layer (#38 stays deferred).
2. On a reliable ordered link, any framing anomaly is a bug or corrupt state,
   so the receiver should disconnect rather than resync.
3. Throughput is out of scope; measure first, add a fast path only if needed.
4. No old clients exist, so firmware and client change together with no shim.

## Approaches Considered
### A: INDICATE + non-blocking send callback + device TX queue (chosen)
Keep `udisplay_send_fn` void and non-blocking. demo05 owns a bounded byte-ring
TX queue drained one fragment per `BLE_GAP_EVENT_NOTIFY_TX` confirmation.
Overflow, mbuf exhaustion, indicate failure or confirmation timeout means
disconnect. Framing errors on receive mean disconnect on both sides.
Effort S/M, risk low.
### B: Make `udisplay_send_fn` return a busy code and add a library pump
Rejected: pushes a retry/pump state machine into libudisplay for a problem that
is specific to NimBLE's one-in-flight rule. TCP and other transports do not need it.
### C: Packet-level ACK layer (#38)
Rejected by the issue: same round-trip cost per message at MTU 512 for a much
larger protocol surface.

## Recommended Approach
A, with these decisions:
- `udisplay_feed()` / `udisplay_ble_feed()` return `int` (0 ok, -1 link error)
  so firmware can disconnect on a framing error. `UDisplay::feed` (generated
  wrapper) is unchanged; demo05 calls `udisplay_feed(ui.ctx(), ...)` directly.
- Client `Proto::bleFeed()` returns a three-state result (More/Done/Error);
  `bleUnframe()` stays as a bool wrapper. `BleTransport` disconnects on Error.
- TX queue is a byte ring inside demo05 (not the library), guarded by a
  critical section that never wraps a BLE call.
- The client-to-device ATT write timeout (TODO-030) is NOT folded in: its own
  entry says the value needs real-device data. Indications make the
  device-to-client half self-policing (ATT 30 s timeout).

## Open Questions
- Qt Bluetooth indication delivery per backend (BlueZ, Android) needs hardware
  verification; not possible in this environment.
- Measurements (blob download time, 1 KB round trip at MTU 512) require ESP32 +
  Android hardware.

## Eng Review (/plan-eng-review, non-interactive)

Scope: 8 files of real change plus docs, no new classes. Complexity gate not tripped. Decisions:

- [P1] (9/10) `libudisplay/src/udisplay.c:200` `udisplay_ble_feed` swallows `BLE_RX_ERROR`
  (`ble_rx_reset(...)` and return). With the disconnect rule the caller must learn
  about it. Fix: return `int`. Same for `udisplay_feed`, including the existing TCP
  overflow branch (`tcp_rx_reset` only), for one consistent contract.
- [P1] (9/10) `udisplay-client/src/Protocol.cpp:382` `bleUnframe` returns `false` for both
  "need more fragments" and "framing error", and a continuation with no first fragment
  (`if (!state.active) return false;`) is not even reset. Fix: `bleFeed()` tri-state.
- [P1] (8/10) demo05 `send_cb` can run from the NimBLE host task, the heartbeat timer task
  and app tasks. The ring and the in-flight flag share one critical section. The BLE call
  itself happens outside it. Only the task that flips `inflight` false to true may call
  `ble_gatts_indicate_custom`, which preserves order.
- [P2] (8/10) `ble_rx_feed` accepts a continuation only when `in_progress`; that case
  already returns `BLE_RX_ERROR`, so it becomes a link error with no library change.
- [P2] (7/10) Ring sizing: 1 KB message at MTU 23 is ~60 fragments (~1.3 KB with length
  prefixes). Use 2 KB; overflow is a link error, not a drop.
- NOT in scope: TODO-030 write timeout, fast-path characteristics, exactly-once across reconnect.

### Test plan
- libudisplay: `udisplay_feed` returns 0 on valid BLE fragment, -1 on flags != 0,
  length > 1024, orphan continuation, wrong offset, wrong packet_id, over-completion;
  TCP overflow returns -1.
- client: `bleFeed` returns More/Done/Error for the same cases; `bleUnframe` unchanged.
- demo05: must compile under ESP-IDF; hardware behaviour unverified here.

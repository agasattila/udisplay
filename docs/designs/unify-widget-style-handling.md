# Design: Unify widget style handling

Generated by /office-hours on 2026-09-14
Branch: main
Repo: agasattila/udisplay
Status: APPROVED
Mode: Builder

## Problem Statement

`style` is overloaded. There's a top-level `style:` YAML block defining named stylesheets
(color tokens — background, text, accent, etc — parsed into `QMap<QString, StyleToken>
m_styles` in `DeviceController`). Separately, `display` and `label` widgets each have their
own `style` property selecting a visual variant (`display: default|large`, `label:
heading|body|caption`) — same key name, unrelated meaning. There's also no way to assign a
named global stylesheet to an individual widget: only one stylesheet is active app-wide at a
time (`setActiveStyle(name)`, exposed to QML as a single `activeStyle` QVariantMap property).

Filed as issue #11 by the maintainer within an hour of PR9 (widget-model-flatten) merging —
that refactor deduplicated a redundant `WidgetDef::style` C++ member into
`WidgetDef::props["style"]`, and doing that surfaced the naming collision directly.

## What Makes This Cool

Not a delight feature in the traditional sense — this is schema hygiene on a young, actively
evolving DSL. The cool part: fixing the naming collision the right way opens a real
capability (themed regions of a dashboard — a panel that carries its own visual identity)
that wasn't reachable before, not just a cosmetic rename.

## Constraints

- Pre-1.0, early-adopter schema — no external YAML authors deployed yet, prior schema
  changes (button-group/dpad split) took clean breaks without back-compat shims.
- Only `Display` and `Label` widgets currently write `props["style"]`
  (`YamlParser.cpp:298`, `:429`); only `DisplayWidget.qml` and `LabelWidget.qml` read it,
  both for variant logic, not stylesheet lookup.
- `style:` block parses before `widgets:` in `YamlParser::parse()`
  (`YamlParser.cpp:796` vs `:804`), so `stylesOut` is available at widget-build time.
- `DeviceController` exposes only the single active named stylesheet to QML today
  (`Q_PROPERTY activeStyle`) — the full `m_styles` registry is not exposed at all.
- TODO-027 (firmware-triggered style switching) is explicitly out of scope — this design
  only touches the client-side schema and rendering, not the wire protocol.

## Premises

1. **The collision is real and worth fixing now.** Confirmed via grep — contained blast
   radius (2 widget types), but it already caused confusion once (surfaced by PR9's own
   refactor) and will get worse as more widgets grow variant properties. *Agreed.*
2. **Scope is both the rename and the feature, minus cascading.** The issue asks for two
   things: (a) rename `display`/`label`'s variant property to `displayStyle`/`labelStyle`,
   and (b) make every widget's `style:` property actually resolve against the global
   stylesheet registry at render time — nothing today lets a widget diverge from the
   app-wide active style. Landing (a) without (b) would leave `style:` in the schema as an
   accepted-but-silently-ignored property, worse than today's ambiguity. *Revised after
   cross-model input (below): container-level cascading (a `row`/`grid`/`section` carrying a
   style for its subtree) is explicitly deferred — v1 covers individual (leaf) widgets only.
   The resolver interface is designed to accept an inherited-style parameter so cascading is
   a later, additive pass, not a rearchitect.*
3. **Clean break, no deprecated alias.** Matches how this project has handled prior
   schema changes; no external YAML files to protect yet. *Agreed.*

## Cross-Model Perspective

Codex's cold read (independent, no visibility into this conversation):

- **Coolest version not yet considered:** themed regions — a container with `style: alarm`
  gives its whole subtree that stylesheet, while a nested widget's own `displayStyle`/
  `labelStyle` variant stays independent. Resolution order: `explicit widget style → nearest
  styled ancestor → app-wide active style`. Follow-up idea: a design-mode preview that
  renders the same subtree under multiple named styles with an "inherited from X" inspector.
- **Scope-changing fact:** the missing QML data path (`DeviceController` exposes only ONE
  active stylesheet, not the full registry) means this is a small rendering-architecture
  change, not a rename. The real acceptance test: two widgets pinned to different styles
  simultaneously, call `setActiveStyle()`, confirm only the un-pinned one moves.
- **Closest existing pattern:** Flutter's scoped `Theme` — nearest-enclosing theme wins,
  descendants react. uDisplay still has to build the integration itself: name resolution
  against `m_styles`, carrying style context through the YAML hierarchy, binding every token
  consumer, notifying on change. Qt's own `palette` property propagates parent→child but
  doesn't know about uDisplay's named stylesheets.
- **Weekend build order:** prove the smallest complete rendering path first (two widgets,
  one inherited one pinned, reactive lookup, live global-switch test) before the rename and
  broader per-widget rollout. Recommended deferring container cascading to a later pass while
  designing the resolver to accept an inherited-style parameter — accepted into Premise 2
  above. Recommended skipping CSS selectors, token-level partial merging, style animations,
  the preview UI, and firmware-triggered switching (TODO-027) for this pass — all deferred.

## Approaches Considered

### Approach A: Runtime lookup (minimal viable)
Rename the variant props; add a new `DeviceController::styleFor(name)` Q_INVOKABLE exposing
the full `m_styles` registry to QML; each widget computes
`effectiveStyle: props.style ? controller.styleFor(props.style) : controller.activeStyle`
inline. Smallest new C++ surface, but no natural path to future cascading and unknown-style
validation lands in QML/JS rather than the parser. (human: ~1 day / CC: ~1.5 hrs)

### Approach B: Row-indexed resolver (ideal architecture) — CHOSEN
Centralize resolution in a Q_INVOKABLE keyed by flat-list row, mirroring PR9's
`childModel(row)` pattern exactly: walks `WidgetModel`'s existing `parentId` chain so
ancestor-style plumbing exists now even though nothing sets container style yet. Reuses the
`generation`-counter reactivity idiom PR9 already proved out (and the matching pitfall —
`qml-invokable-no-notify-binding-staleness` — logged from that session). Biggest diff of the
three, and needs a layering decision up front (does `DeviceController` reach into
`WidgetModel`, or does `WidgetModel` grow a style-aware method) — but cascading later becomes
a one-line follow-up instead of a rearchitect. (human: ~2-4 days / CC: ~3-5 hrs — a range,
not a point estimate, because it's pre-decision: re-scope after the layering call and the
17-file widget touch list are confirmed, since not every widget file necessarily needs the
change)

### Approach C: Parse-time resolution (creative/lateral)
Resolve each widget's explicit `style:` into a baked `props["_resolvedStyle"]` map at parse
time (`stylesOut` is already available then). Zero new C++ API, zero new QML reactivity —
reuses the existing `props`/`PropsRole` `dataChanged` path. Un-pinned widgets are completely
untouched. Cascading later is cheap since `buildWidget()`'s existing recursive walk already
threads `parentId`. Tradeoff: a device reconnect is needed to see a *redefined* stylesheet's
colors reflected on already-pinned widgets (matches how every other `props` value already
behaves). (human: ~3-4 hrs / CC: ~45 min)

## Recommended Approach

Session recommendation was Approach C (smallest, safest diff, reuses existing
infrastructure end-to-end, cascading is cheaper later since the tree walk already exists).

**User chose Approach B** — deliberate tradeoff: bigger diff and more new C++ surface now, in
exchange for reusing a pattern this codebase just battle-tested in PR9 (row-indexed
Q_INVOKABLE + generation counter) rather than inventing a second reactivity idiom, and for
making container cascading a clean additive follow-up rather than requiring the parse-time
resolution model to be reworked into a runtime one later if cascading turns out to need live
reactivity (e.g. a device pushing a redefined stylesheet at runtime without a full reconnect).

## Open Questions

- ~~Layering~~ **RESOLVED during `/plan-eng-review`:** the resolver lives on
  `DeviceController`. Verified `DeviceController.h:113,125,234` already owns both `m_styles`
  and `m_model` (the `WidgetModel` instance) — the resolver reads `widgetModel()->data(row,
  PropsRole)` internally, no new dependency. Putting it on `WidgetModel` would require
  threading `m_styles` into `WidgetModel`, inverting today's ownership direction for no
  benefit.
- ~~Missing-token fallback~~ **RESOLVED during `/plan-eng-review`:** not actually an open
  question. Verified `YamlParser.cpp:723` (`parseStyles()`): every named stylesheet already
  starts as `StyleToken t = defaults;` — a full copy of `style.default:` — before any
  per-field override applies. `m_styles` never holds a partial `StyleToken`; Codex's concern
  (borrowing from the active theme) doesn't apply to how this parser actually works.
- **NEW, added during `/plan-eng-review`, then corrected:** only TRULY transparent
  containers reject `style:` with a parser diagnostic in v1 — `row`, `grid`, `dpad`, `button`
  (verified `color: "transparent"` in `RowWidget.qml`/`GridWidget.qml`/`DpadWidget.qml`/
  `ButtonWidget.qml`, zero own-chrome rendering, `style:` would be a genuine no-op there,
  the exact "accepted-but-silently-ignored" anti-pattern Premise 2 was written to avoid).
  `section` and `button-group` are NOT in this list — both already render their own chrome
  from `activeStyle` (`SectionWidget.qml`'s header/border via `surface`/`accent`/`line`;
  `ButtonGroupWidget.qml`'s selection chrome via `text_muted`/`button`/`border`/
  `button_text`), so `style:` on them has a real, meaningful, non-cascading effect now —
  coloring the container's own chrome, independent of and forward-compatible with cascading
  to children later. Lifting the row/grid/dpad/button restriction later when cascading ships
  is a non-breaking schema loosening.
- **NEW, added during `/plan-eng-review`:** the resolver's QML binding needs BOTH
  `controller.activeStyle` (existing NOTIFY, fires on `setActiveStyle()`/reconnect) AND
  `controller.widgetModel.generation` (existing NOTIFY from PR9, fires on `setWidgets()`/
  `clear()`) as reactive dependencies — row indices are not stable across a reparse
  (`WidgetDef.h`'s own doc: `parentId` only valid until the next `setWidgets()`), so binding
  on `activeStyle` alone would leave the resolved style stale after a full YAML reload. This
  is the same staleness bug class PR9's adversarial review already caught once for
  `childModel()` — verify it doesn't recur here.
- ~~Runtime stylesheet redefinition~~ **RESOLVED during `/plan-eng-review`:** structurally
  impossible to be partial. Verified `DeviceController::applyParsedYaml()`: `m_styles =
  styles;` and `m_model.setWidgets(widgets);` always happen together, in the same function,
  on every single parse (design-mode reload AND real device reconnect both go through this
  one path) — there is no code path that changes `m_styles` without also fully resetting the
  widget model (bumping `generation`). So "redefinition without a full reparse" never
  happens; Approach B's stated edge over Approach C for this specific scenario doesn't
  actually exist (both would see redefinition identically, via reparse) — noted honestly
  here without reopening the B-vs-C decision, which had other valid reasons (reuse of the
  `childModel(row)`/`generation` pattern, cleaner future cascading path). The acceptance test
  that DOES matter and was missing: `setWidgets()` with unchanged widgets but a redefined
  `m_styles` value — confirm the resolver picks up the new colors on both pinned and
  unpinned widgets. Added to Next Step 6's test list.

## Success Criteria

- `display`/`label` widgets use `displayStyle`/`labelStyle` for variant selection; `style`
  means "reference to a global stylesheet" everywhere in the schema, with no other meaning.
- Every widget type EXCEPT row/grid/dpad/button accepts an optional `style:` property
  naming a stylesheet from the top-level `style:` block; row/grid/dpad/button reject it with
  a diagnostic (truly transparent, `style:` would be a no-op — see Open Questions); an
  unknown stylesheet name on any accepting type produces a parser diagnostic naming the
  widget.
- Acceptance test (from Codex, adopted): two widgets rendered simultaneously with different
  `style:` values; calling `setActiveStyle()` changes only the widget that has no explicit
  `style:` set. Pinned widgets stay pinned. Plus (added during `/plan-eng-review`): a
  reparse with unchanged widgets but a redefined `m_styles` value updates both pinned and
  unpinned widgets' resolved colors correctly.
- Container-level style cascading (a row/grid/section styling its subtree) is explicitly
  out of scope for this pass — the resolver interface accepts an inherited-style parameter
  so it can be added later without a rearchitect, but nothing sets or consumes it yet.
  **Shipped in a follow-up pass:** issue #20 / TODO-055 /
  `docs/designs/container-style-cascading.md`.

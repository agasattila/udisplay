# Design: Assign a widgetId to every widget (issue #43)

Generated by /office-hours on 2026-09-25

## Problem Statement

Only "leaf" widgets get a protocol `widget_id` today. Containers (`section`,
`row`, `grid`, `dpad`) and decorations (`label`, `separator`) are skipped by
both independent ID derivations (`udisplay-gen/udisplay_gen/widget_ids.py` and
`udisplay-client/src/YamlParser.cpp`), so they get `widgetId = 0` in the
client and no `WIDGET_ID_*` constant in the generated firmware API.

Since PR #22 containers own properties that affect their subtree (`style:`
cascades). `ENABLED` / `VISIBLE` are already defined as "all widgets" in the
Standard Properties table (docs/protocol.md), but a firmware author cannot
target a container or a label with `SET_PROPERTY` / `RESET_PROPERTY` because
there is no ID to send. The YAML model and the runtime property model disagree.

## Premises

1. Addressability is a property of *every* widget, not of interactive widgets.
   The issue asks for "every widget, including structural/container widgets",
   so `label` and `separator` get IDs too (a label is the obvious future target
   of a "label text" property, a separator of `VISIBLE`).
2. Existing firmware code must keep compiling: every `WIDGET_ID_*` *name* that
   exists today keeps the same name, unless a container/decoration name now
   collides with a generated identifier (rejected at codegen with a clear
   error, see Eng Review OV4). Numeric values shift, and that is a wire
   change: see Eng Review OV1 (PROTO_VERSION 0x05 + client legacy mode).
3. The 0x10..0xFF range (240 slots) stays. Containers and decorations now
   count against it. Real dashboards (all 5 demos: 10-24 IDs after the change)
   are nowhere near the cap.
4. The client and codegen must keep deriving identical IDs, enforced by the
   shared golden fixtures in `tests/protocol_vectors.json`.

## Approaches Considered

### Approach A: Container gets its own path, children stay transparent (chosen)
A container/decoration's ID path is `<transparent prefix>.<own key>`, exactly
like a leaf at the same position. Its children's paths are unchanged (the
container's key is still *not* a segment of a child's path).
- Effort S/M, risk low. No existing `WIDGET_ID_*` name changes.
- New collision class: a container key equal to a leaf key elsewhere in the
  same transparent scope (e.g. a section `advanced` and a slider `advanced`
  in another section). Caught by the existing duplicate-path check in both
  derivations, with a clear error. None of the demos collide.

### Approach B: Hierarchical paths (container names become path segments)
Every child's path includes its containers (`advanced.rate`).
- Rejected: renames nearly every existing `WIDGET_ID_*`, breaks every
  firmware sketch, and contradicts the documented "containers are
  ID-transparent" naming rule for zero functional gain.

### Approach C: Containers only, decorations stay ID-less
- Rejected: the issue explicitly says every widget; keeping a second
  "no ID" category keeps the special case the issue wants removed.

## Recommended Approach (A), concretely

**ID assignment (both derivations, kept in lockstep):**
- `widget_ids._collect()` / `YamlParser.cpp collectPathsRecursive()`: emit a
  path for every widget map entry regardless of type. Containers still
  recurse with the unchanged prefix. Button-group items keep their IDs;
  dropdown items are options, not widgets, and stay ID-less.
- `NO_ID_TYPES` goes away; duplicate-path and >240 errors keep working and
  their messages mention containers/decorations.
- Button-face children that are containers (`row`/`grid` inside a button)
  also get IDs (`btn.face_row`), children still prefixed by `btn`.

**Client runtime:**
- `WidgetDef.widgetId` is non-zero for every row (sections, rows, grids,
  dpads, labels, separators). `WidgetModel::m_idToRow` then indexes them,
  so `SET_PROPERTY` / `RESET_PROPERTY` reach containers with no protocol
  change.
- `VISIBLE` on a container already hides its subtree (children render inside
  the container's delegate).
- `ENABLED` on a container becomes effective for the subtree: `EnabledRole`
  walks the `parentId` chain (same shape as `VisibleRole`'s collapsed-section
  walk) and `setProperty`/`resetProperty` emit `dataChanged` for the
  descendants, mirroring `toggleSection()`.

**Generated firmware API:**
- C / MicroPython: a `WIDGET_ID_*` constant for every widget. No typed
  setters/handlers for containers/decorations (they carry no value); generic
  `udisplay_set_property()` / `reset_property()` works on the ID.
- `collect_types()` reports the real type (`section`, `row`, `label`, ...) for
  the new entries; backends that key typed code off the type map must ignore
  types they have no setter/handler for.
- C++ / MicroPython object APIs: every widget becomes a member; containers
  and decorations are plain `Widget` members with `set_property()` /
  `reset_property()` (see Eng Review A1/A4 — supersedes the original
  "deferred" call).

**Docs:** protocol.md (ID assignment + range text), widgets.md (every "no
widget ID" note), udisplay.schema.json descriptions, merkle.md if it states
the rule.

## Open Questions (deferred, not blocking)

- Runtime `STYLE` (0x04) semantics are still TBD in protocol.md; once defined,
  a container target cascades via the PR #22 resolver for free.
- Named convenience wrappers (`set_visible(bool)`, `set_enabled(bool)`) on
  top of the generic `set_property()`; separate PR.

## Success Criteria

- Every widget in a parsed YAML has a unique non-zero ID in 0x10..0xFF, and
  codegen + client agree (golden fixtures extended with containers,
  decorations, button-face rows, dpads).
- `SET_PROPERTY(VISIBLE/ENABLED)` on a section/row hides/disables its subtree
  in the client (unit test on WidgetModel).
- No existing `WIDGET_ID_*` name disappears in the demos' generated headers.
- All three test suites green.

### Step 0: scope

- Existing code already solves most of it: both ID walkers exist and are
  mirrored, `WidgetModel::m_idToRow` already indexes any non-zero ID, and
  `SET_PROPERTY`/`RESET_PROPERTY` already route through `indexForWidgetId()`.
  The change mostly deletes the `continue` that skips containers and
  decorations.
- Touches more than 8 files (2 ID walkers, validate.py, 2 backends, client
  model, fixtures, docs). That is breadth, not new abstractions: no new
  classes or services in the client. Proceeding at full scope.
- TODO cross-reference: **TODO-007** (dedupe `CONTAINER_TYPES` /
  decoration sets) is bundled, since this PR removes `NO_ID_TYPES` anyway and
  the backends need the same set. TODO-038 (unbounded nesting depth) is
  NOT closed by this change: the 240 cap is checked after the recursive walk
  (see OV5).

### 1. Architecture

- **A1 [P1] (confidence 9/10) C++ backend cannot reach container IDs.**
  `cpp_backend.py` emits no `WIDGET_ID_*` constants. Firmware reaches widgets
  only through typed members, and the base class has no public id
  (`class Widget { protected: udisplay_t* _ctx; uint8_t _id; ...`). If
  containers stay out of the member list, issue #43 does nothing for C++
  firmware. **Decision:** the base `Widget` gets public `id()`,
  `set_property(prop, v)`, and `reset_property(prop)`, which call
  `udisplay_set_property(_ctx, _id, ...)`. Every widget becomes a `UDisplay`
  member (containers and decorations as plain `Widget`, in YAML declaration
  order). This supersedes the design doc's "C++/Python members deferred"
  open question.
- **A2 [P1] (confidence 9/10) C++ `_cpp_ordered_toplevel` misses `dpad`.**
  Its local `container_types = {"section", "row", "grid"}` has no `dpad`, so
  a top-level dpad's child buttons never become members. The same comment in
  `python_backend.py` flags this. The rewrite in A1 routes through the shared
  `CONTAINER_TYPES` (TODO-007), which fixes it as a side effect. A
  regression test covers it.
- **A3 [P1] (confidence 9/10) Button sub-members assume LED.**
  `_cpp_generated_classes` emits `LedWidget {sub_key};` for every face child,
  and `_py_instantiate` defaults unknown sub-types to `LedWidget`. Once face
  labels and face rows are in `widget_ids`, that emits a label as an LED.
  **Decision:** sub-member type comes from the same type-to-class map as
  top-level members (display, rgbled, led, and `Widget` for containers and
  decorations).
- **A4 [P2] (confidence 8/10) MicroPython object API.** Wrapper classes have
  no `set_property`. **Decision:** add a `Widget` base in the generated
  `ui.py` with `set_property` / `reset_property`, have the typed wrappers
  subclass it, and add containers and decorations as `Widget` members.
- **A5 [P2] (confidence 8/10) ENABLED on a container is a no-op today.**
  `VisibleRole` already hides a subtree, because children render inside the
  container delegate. `EnabledRole` returns `w.enabled` only, and the
  row/grid/section QML components don't take `enabled`. **Decision:**
  `EnabledRole` becomes "self and every ancestor enabled", using the same
  parentId walk as `VisibleRole`. `setProperty` / `resetProperty` on
  ENABLED or VISIBLE also emit `dataChanged` for all descendants. This
  mirrors `toggleSection()`.

Failure scenario considered: firmware built from an old header against a
new client blob. It cannot happen, because the header and the blob come from
the same codegen run and the Merkle root pins both.

### 2. Code quality

- **Q1 [P2] (confidence 9/10) validate.py uniqueness skips containers and
  decorations.** `_semantic_errors_in_map` does `continue` for
  `CONTAINER_TYPES` and `DECORATION_TYPES` before the `seen_names` check, so
  a section named the same as a slider passes `validate` and fails later in
  `assign()`. **Decision:** containers and decorations join `seen_names`
  (a container adds its own key before recursing).
- **Q2 [P3] (confidence 9/10) Stale comments.** Comments that say
  "widgetId=0 means decoration/container" (WidgetModel.cpp:23, WidgetModel.h:18),
  the golden-fixture test's `!= 0` filter, the `isDecoration` comment, and
  the widget_ids.py docstring are updated in the same commit.

### Outside voice (Codex) — all five accepted

- **OV1 [P1] Wire compatibility.** The Merkle root pins the YAML bytes, not
  the ID algorithm. Old firmware + new client would re-derive shifted IDs
  from an unchanged blob, and events would hit the wrong handlers.
  **Decision:** bump `PROTO_VERSION` to 0x05 (libudisplay, client,
  MicroPython runtime). The client keeps the leaf-only ("legacy") ID scheme
  for devices whose HANDSHAKE reports a version below 0x05. Old clients
  reject v5 devices with the existing "Update the app" error. The current
  golden fixtures are kept as `widget_id_fixtures_legacy` and checked against
  the client's legacy mode. The new fixtures cover the v5 scheme. The
  header and libudisplay must come from the same release (documented).
- **OV2 [P1] QML won't disable rendered subtrees.** DpadWidget reads
  `ChildModel::get()` snapshots, and the section header has no enabled
  binding. **Decision:** `WidgetDelegate.qml` binds `enabled: _enabled` on
  the delegate itself. Qt Quick's enabled propagation then disables every
  descendant item, including dpad cells and the section collapse MouseArea.
  DpadWidget also re-reads its snapshots on the child model's
  `dataChanged`. A QML test covers a disabled container.
- **OV3 [P1] C++ `Widget` constructor is protected.** Only `UDisplay` is a
  friend, so a generated button subclass cannot construct a plain `Widget`
  member. **Decision:** make the constructor public. A new
  `test_generated_compiles.py` compiles a fixture with face decorations,
  face rows, dpad, and sections using g++ -fsyntax-only (plus gcc for the C
  header).
- **OV4 [P2] New identifier collisions.** A section named `init` would now
  clash with `UDisplay::init()`, and a face child named `set_property` would
  shadow the new method. **Decision:** the C++ backend gains a
  reserved-name check (UDisplay methods/fields; Widget methods for
  sub-members) that raises a clear `ValueError`. The Python reserved sets
  gain `id`, `set_property`, and `reset_property`.
- **OV5 [P2] Nesting-cap claim was wrong.** It has been dropped (see Step 0).
  TODO-038 stays open as-is.

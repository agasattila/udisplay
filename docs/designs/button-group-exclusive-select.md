## Problem Statement

`button-group` exists as its own widget type only because of exclusive-select
semantics, and those are not implemented. Every backend generates a group with
no setter (`cpp_backend.py` emits a bare `Widget`, `python_backend.py`'s
`ButtonGroupWidget` says "No .set()", the C backend has no `_SETTER_TYPES`
entry). The client already renders a selection ring when the group's `value`
equals an item's widget ID (`ButtonGroupWidget.qml`), but nothing on the device
side can ever produce that value. Result: in every deployment (demo01-04) all
items are permanently unselected.

## Constraints

- Device-authoritative state (widgets.md Design Principle 1): a press sends the
  item's normal BUTTON_PRESS/RELEASE/CLICK events; the client never commits the
  selection itself. Selection changes only when firmware sends STATE_UPDATE.
- No wire-format change and no PROTO_VERSION bump: reuse STATE_UPDATE with the
  existing `uint8` value type.
- Three codegen backends (C, C++, Python/MicroPython) must stay in lockstep.
- C++ backend targets C++11 (no C++17 features).

## Premises

1. The payload is the **selected item's widget ID**, not a positional index.
   The client's QML already compares `value === model.widgetId`, widget IDs
   are the protocol's only identifiers (flat ID space), and the C/Python
   backends already emit a symbolic `WIDGET_ID_<GROUP>_<ITEM>` constant per
   item. An index would need a new index->child mapping on the client, and
   would reintroduce the "which order: YAML or alphabetical?" ambiguity.
2. Value `0x00` means "no selection". IDs 0x00-0x0F are reserved and never
   assigned to a widget, so 0 can never collide with a real item. The client
   needs no special-casing: no item's widgetId equals 0, so nothing is ringed.
   This is also the initial state (value is null until the first STATE_UPDATE).
3. The client needs no protocol changes. `DeviceController::onStateUpdateData`
   already maps `VAL_UINT8` to an int `value` on the group's row. The client
   work is a round-trip contract test, not new code.
4. `set` and `clear` become reserved button-group item keys (they are methods on
   the generated C++/Python group object; an item with that key would shadow
   them). Enforced in `validate.py` so every backend gets the same error.

## Approaches Considered

### Approach A: Copy the dropdown pattern (index-valued enum)
`set(Option)` with 0..N-1 indices. Rejected: the client would need an
index->widgetId mapping that doesn't exist, and `ButtonGroupWidget.qml` already
assumes widget IDs.

### Approach B: Item widget ID as the value, per-backend symbolic API (chosen)
- **C**: `set_<group>(udisplay_t* ctx, uint8_t item_id)` + `clear_<group>(ctx)`,
  `static inline`, sending `udisplay_send_uint8`. Symbolic values are the
  existing `WIDGET_ID_<GROUP>_<ITEM>` macros.
- **C++**: the group class gains a scoped `enum class Item : uint8_t { fast =
  0x12u, ... }` (values = item widget IDs, type-safe per group, same shape as
  dropdown's `Option`), `void set(Item)` and `void clear()`.
  Firmware: `ui.mode_sel.set(ModeSelWidget::Item::fast)`.
- **Python**: `ButtonGroupWidget.set(item)` accepts the item object
  (`ui.mode_sel.set(ui.mode_sel.fast)`) or a raw `WIDGET_ID_*` int;
  `clear()` sends 0.
- Effort: M (human ~1 day / CC ~30 min). Risk: Low. No wire change.

### Approach C: Client-side optimistic selection plus firmware veto
Rejected by the issue itself and by Design Principle 1.

## Recommended Approach

Approach B. Deliverables:

1. Codegen (all three backends) as above, plus `validate.py` reserving
   `set`/`clear` as item keys.
2. Tests: udisplay-gen unit tests per backend (setter emitted, constants,
   dispatch unchanged, reserved-name rejection, generated C/C++ compiles);
   client round-trip test: STATE_UPDATE(group, uint8 item_id) -> model value
   -> QML item shows the selected ring; `0` clears; a press does NOT change
   `value`.
3. Docs: `docs/widgets.md` button-group section (event -> firmware decision ->
   setter -> STATE_UPDATE flow, C/C++/Python examples), widget summary table,
   `docs/protocol.md` STATE_UPDATE notes, schema description ("at most one
   active item; none until the device sets one").
4. Demos 01-04: press handlers call the setter (firmware confirms), and the
   initial selection is pushed from `on_client_ready`, so the demos exercise
   the full round-trip.
5. TODOS.md: close TODO-006.

## Out of scope

- `debug_state` preview for button-group in design mode (schema has no
  `debug_state` on button-group today). Follow-up if requested.
- Validating on the client that the received ID is actually a child of the
  group. An unknown ID renders as "no selection", which is safe.

## Success Criteria

- Firmware in each backend can select, change, and clear the group selection
  using symbolic names only (no raw numbers).
- A client test fails if the QML/controller path stops rendering the
  STATE_UPDATE-confirmed selection, or if a press starts committing it locally.
- All three subproject test suites pass.

**A1 [P1] (confidence: 10/10) `udisplay-gen/udisplay_gen/backends/c_backend.py`: generated C setter bodies always pass `v`**, whatever the argument is called in `_SETTER_TYPES`. Probed: an rgbled-only YAML generates
`static inline void set_s(udisplay_t* ctx, int32_t rgb) { udisplay_send_int(ctx, WIDGET_ID_S, v); }` and gcc fails with `'v' undeclared`. dropdown (`uint8_t index`) has the same bug. Existing tests only grep the header text; none compile it. The new `uint8_t item_id` setter would hit this too.
Decision: fix it at the source. Take the parameter names from the arg declaration so every setter goes through one path. This fixes rgbled and dropdown as a side effect, and gets called out in the PR.

**Q1 [P2] (confidence: 9/10) Reserved item keys.** `set`/`clear` as button-group item keys would collide with the new C++ methods and Python attributes (Python's `_BUTTON_GROUP_RESERVED_NAMES` = `{"_device", "_widget_id"}` today).
Decision: reject them in `validate.py` (one check, every backend) and add them to the Python reserved set so the Python-side guard stays accurate.

**Q2 [P3] (confidence: 8/10) Stale comments.** `ButtonGroupWidget.qml` header ("`value` is currently unimplemented on the firmware side"), `python_backend.py` "No .set()", the schema's "Exactly one item is active", and widgets.md "The group itself has no setter" all go stale.
Decision: update all of them in the same change.

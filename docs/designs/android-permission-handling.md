## Problem Statement
uDisplay Client's Android runtime permission handling is incomplete, so device
discovery silently fails for some users on some Android versions. Issue #15
(github.com/agasattila/udisplay/issues/15) tracks this with explicit tasks and
acceptance criteria.

## Status Quo (evidence, not assumption)
Read the actual code before proposing anything (`src/main.cpp`,
`src/BleScanner.cpp`, `src/MdnsScanner.cpp`, `android/AndroidManifest.xml`):

1. `AndroidManifest.xml` correctly *declares* the full permission set per
   Android version (BLUETOOTH/BLUETOOTH_ADMIN maxSdk 30, BLUETOOTH_SCAN/
   BLUETOOTH_CONNECT minSdk 31, ACCESS_FINE_LOCATION/ACCESS_COARSE_LOCATION
   unconditionally) — this part is already right and well-commented.
2. `main.cpp` requests `QLocationPermission` once, at app startup, before the
   user has opened the discovery screen. The callback is empty on Denied —
   nothing is surfaced to the UI or logged.
3. `QBluetoothPermission` is `#include`d in `main.cpp` but **never
   requested anywhere in the codebase** (verified via repo-wide grep for
   `requestPermission`). Declaring `BLUETOOTH_SCAN`/`BLUETOOTH_CONNECT` in the
   manifest does not grant them at runtime on API 31+ — Android still requires
   an explicit runtime prompt.
4. `BleScanner.cpp:38-43` carries a comment claiming "Qt 6.5+ surfaces runtime
   permission requests automatically through
   QBluetoothDeviceDiscoveryAgent::start() — no explicit request needed here."
   This is an unverified, uncited claim, and it contradicts Qt's own
   documented permission model (permissions must be requested via
   `qApp->requestPermission()`; agents do not request permissions on your
   behalf). This claim is the root cause of the issue: on Android 12+, BLE
   scanning silently returns zero results because `BLUETOOTH_SCAN` was never
   granted, and nothing tells the user why.
5. `MdnsScanner.cpp` has **no Android-awareness at all** — no permission
   check, no gating of `startScan()` on any grant. Wi-Fi/mDNS discovery
   (NSD) on Android also depends on location (or `NEARBY_WIFI_DEVICES` on
   API 33+ as an alternative) being granted; today it's not checked.
6. The good news: `IScanner::scanError` → `DiscoveryModel::scanError` →
   `DiscoveryScreen.qml` plumbing already exists and is wired up. Permission
   failures just need to be routed into it — no new UI-facing surface is
   required.

## Premises
1. The manifest's permission *declarations* are already correct per Android
   version and do not need to change — agree.
2. The defect is at the *runtime request* layer: permissions are declared
   but a required one (`QBluetoothPermission`) is never requested, and the
   one that is requested (`QLocationPermission`) is requested too early, with
   its result discarded — agree.
3. Qt's `QPermission` classes already internally map to the correct concrete
   Android permission group per API level (Qt's android deploy tooling does
   this dispatch) — so no hand-rolled `QOperatingSystemVersion` branching is
   needed in application code, only correct use of the existing Qt
   permission API at the right place with the result handled — agree,
   confirmed against Qt Bluetooth/Positioning permission docs referenced in
   the existing manifest comments' own framing.
4. "Handle denied/missing permissions gracefully" means: route to the
   existing `scanError` signal with an actionable message, and gate scan
   start on a granted/undetermined check rather than firing the OS dialog
   unconditionally at app launch — agree.

## Approaches Considered

### Approach A: Point-of-use permission requests through existing scanError plumbing (minimal viable)
Summary: Move permission requests out of `main.cpp` startup into each
scanner's `startScan()`. `BleScanner::startScan()` requests
`QBluetoothPermission` (+ `QLocationPermission` if not already granted)
before starting the discovery agent; only calls `m_agent->start()` once
granted. `MdnsScanner::startScan()` requests `QLocationPermission` the same
way before starting NSD. On `Denied`, emit `scanError` with an actionable
message ("Bluetooth permission denied — enable it in Android Settings to
discover devices") instead of silently doing nothing. On `Undetermined`,
request and continue asynchronously in the callback.
Effort: S (human: ~3-4 hrs / CC: ~25 min)
Risk: Low
Pros:
- Reuses the `scanError` → QML plumbing that already exists and is tested by users today
- Touches only the two scanner classes + removes the dead code in `main.cpp` — small, reviewable diff
- Matches every acceptance criterion in issue #15 directly
Cons:
- Some duplication between `BleScanner` and `MdnsScanner` (each does its own permission dance)
Reuses: `IScanner::scanError` signal, `DiscoveryModel`/`DiscoveryScreen.qml` error surface, Qt's existing `QPermission` API

### Approach B: Shared AndroidPermissions helper class (ideal architecture)
Summary: Same runtime behavior as A, but factor permission request/track/
gate logic into a small shared `AndroidPermissions` class (Android-only,
`#ifdef Q_OS_ANDROID`) that both scanners call, with a QML-exposed
"permission state" property so the UI can show a persistent "enable
permission" banner (not just a transient error string) and deep-link to app
settings.
Effort: M (human: ~1-2 days / CC: ~1.5 hrs)
Risk: Low-Med
Pros:
- No duplicated permission-dance logic between scanners
- Reusable for future permission needs (e.g. `NEARBY_WIFI_DEVICES` on API 33+, `POST_NOTIFICATIONS`)
Cons:
- New abstraction + new QML-facing surface for a two-call-site problem — more than issue #15 asks for
- Larger diff, more review surface, for a project that has exactly two permission call sites today

### Approach C: QML-declarative permissions (Qt.labs permission QML types)
Summary: Move permission requests into `DiscoveryScreen.qml` directly using
Qt's QML `BluetoothPermission`/`LocationPermission` types, keeping
permission UI and logic co-located in QML instead of C++.
Effort: M (human: ~1 day / CC: ~1 hr)
Risk: Med
Pros:
- Keeps permission-triggered UI (banners, retry buttons) in one QML file
- Idiomatic for Qt Quick apps
Cons:
- Splits permission *decision* logic (should we even scan?) into the UI layer, away from where scanning actually happens in C++ — scanners can no longer independently guard their own `startScan()`
- Bigger structural change than the bug warrants; couples scanner internals to a specific QML screen

## Recommended Approach
**Approach A.** It fixes exactly what issue #15's acceptance criteria ask
for — correct per-version permission requests, graceful denial handling, no
silent failure — with the smallest, most reviewable diff, by finishing the
wiring the codebase already mostly has (declared permissions, `scanError`
plumbing). Approach B's shared helper is reasonable engineering but
premature for two call sites; Approach C moves scan-gating logic to the
wrong layer. If a third scanner or a third permission type shows up later,
extracting a shared helper from A's two call sites is a trivial follow-up
(YAGNI now, not never).

## Open Questions
None blocking — issue #15's acceptance criteria are unambiguous and the
codebase evidence above resolves every implementation question. Follow-up
(not blocking this PR): should `NEARBY_WIFI_DEVICES` (API 33+) be added as
an alternative to `ACCESS_FINE_LOCATION` for mDNS-only discovery, to avoid
asking users for location just to find devices on Wi-Fi? Left as a future
enhancement since `ACCESS_FINE_LOCATION` already works on all supported API
levels per the existing manifest comment.

## Success Criteria (= issue #15 acceptance criteria)
- Required permissions are correctly determined for each supported Android version
- All necessary runtime permissions are requested before the corresponding functionality is used
- Missing or denied permissions do not result in silent failure (surfaced via `scanError`)
- Device discovery works correctly across supported Android versions (BLE
  gated on the fix in this PR; mDNS already works unconditionally — see
  Review Findings & Revisions)

## Review Findings & Revisions (from /plan-eng-review + Codex outside voice)
Codex's independent read (repo access failed on its side, so these are
general Qt/Android-knowledge findings, not repo-verified — cross-checked
against this repo below) caught a real premise error and several concrete
implementation gaps. Auto-decided (non-interactive session, per user
instruction) rather than stopping to ask — recorded here for the record:

1. **mDNS/NSD does not need a location-permission gate — dropped from scope.**
   I conflated Wi-Fi *scan-result* APIs (`WifiManager.getScanResults()`,
   which do need `ACCESS_FINE_LOCATION` historically) with NSD/mDNS *service
   discovery* (`NsdManager`), which does not require location on any
   currently-supported Android version. Gating `MdnsScanner::startScan()` on
   location would have broken Wi-Fi discovery for users who deny location —
   directly violating issue #15's "device discovery works correctly"
   criterion. **`MdnsScanner.cpp` is out of scope for this PR** — it already
   works without a permission gate. (confidence: 8/10 — documented Android
   platform behavior, not verified against a live device from this
   environment)
2. **`QBluetoothPermission` must explicitly set `communicationModes` to
   `Access` only.** Its default requests `Access | Advertise`; this app only
   scans (central role), and the manifest declares no `BLUETOOTH_ADVERTISE`.
   Requesting the default would ask for a permission the app never
   declared. Implementation must call
   `.setCommunicationModes(QBluetoothPermission::Access)` explicitly.
3. **Keep the explicit separate `QLocationPermission` request (already
   planned in Approach A) rather than relying on `QBluetoothPermission` to
   cover it.** Newer Qt (6.8.1+, relevant to this repo's Android CI kit per
   TODOS.md's Qt 6.11 target) stops bundling a location request inside
   `QBluetoothPermission` on API 31+. The manifest's own comment already
   establishes why this app still needs location explicitly (BT address as
   uniqueId, no `neverForLocation`) — Approach A's separate request is
   correct and now required, not just convenient.
4. **Permission-request lifecycle needs explicit state, not just "continue
   in the callback."** Must guard against: `startScan()` called again while
   a permission request is pending (no duplicate dialogs); `stopScan()`
   called while pending (must cancel/ignore the late callback, not start
   scanning after the user navigated away); `_started`/availability-timer
   state must NOT flip true until permission is actually granted and the
   agent actually starts.
5. **The "silent failure" root cause is a documented hypothesis, not a
   confirmed observation** — this repo has no Android device/emulator
   available in this environment to reproduce it. `QBluetoothDeviceDiscoveryAgent::Error`
   already has a dedicated `MissingPermissionsError` value (confirmed:
   `/usr/include/.../qbluetoothdevicediscoveryagent.h:33`), and
   `BleScanner::onAgentError` already forwards any error via `scanError`.
   Whether Qt actually emits that error today, or whether the agent just
   returns zero results with no error at all when `BLUETOOTH_SCAN` was
   never granted, is exactly what real-device QA must confirm — added as a
   verification requirement below rather than assumed.
6. **Test/QA plan expanded** per finding 5 and 7: fresh grant, denial +
   Settings retry, cancellation mid-prompt, and confirming whether
   `MissingPermissionsError` fires today, all require a real Android 12+
   device/emulator — CTest on this desktop Linux build cannot exercise any
   of this. Flagged explicitly as a manual-QA-only gap, not deferred
   silently.

## What already exists

  error surface (already implemented and unit-tested via `MockScanner` in
  `test/test_discovery_model.cpp`) — this PR routes permission failures into
  it, adds no new plumbing.
- `AndroidManifest.xml`'s per-version permission declarations — already
  correct, unchanged by this PR.
- `MdnsScanner.cpp` — already correct for its actual permission
  requirements (none); this PR does not touch it (see Finding 1 above).

## NOT in scope
- `MdnsScanner.cpp` changes — dropped per Finding 1; it needs no permission
  gate.
- `NEARBY_WIFI_DEVICES` / `ACCESS_LOCAL_NETWORK` (API 33+/36+ alternatives
  to location for Wi-Fi-adjacent permissions) — noted as a future
  enhancement in Open Questions, not required by issue #15's acceptance
  criteria for currently-supported API levels.
- A shared `AndroidPermissions` class (Approach B) — YAGNI for the single
  remaining call site (`BleScanner` only, after Finding 1 removed the

  sideload APK, no emulator matrix). Manual QA only, documented as a gap
  rather than silently skipped.

# Design: MicroPython backend for udisplay-gen

Generated by /office-hours on 2026-09-11
Branch: main
Repo: agasattila/udisplay
Status: APPROVED
Mode: Builder

## Problem Statement

`udisplay-gen` has two codegen backends today — `c_backend.py` and `cpp_backend.py`
— both targeting embedded C/C++ firmware. Neither can be used by a MicroPython
developer. Two demos in this repo are already placeholders blocked specifically on
this gap: `demos/demo04` (desktop CPython emulator) and `demos/demo06` (ESP8266
over WiFi TCP, explicitly targeting an 80KB usable RAM budget). `docs/history-roadmap.md`
lists the MicroPython backend as a **v1.0 release blocker**, not a deferred v2 item.

The ask: a third `udisplay-gen` backend (`--lang micropython` or similar) that
produces Python code compatible with MicroPython's constrained runtime on at least
ESP8266 and ESP32, where the same generated application code also runs unmodified
on desktop CPython (matching the existing demo01-03 pattern: same YAML, same
simulated behavior, different backend output).

**Note on a stale label:** `docs/history-roadmap.md` (the actual versioning
document, with a defined `v0.9`/`v1.0`/`v2.x` scheme) places this in `v1.0`.
`demos/demo04/README.md` and `demos/demo06/README.md` both instead call it a
"(v2 scope item)" — this contradicts the roadmap and is treated here as stale
text in the two placeholder READMEs, not as a real scope signal; flagging
rather than editing those files unprompted.

## What Makes This Cool

Right now, getting a custom device UI on uDisplay means writing C or C++. This
backend collapses that to: write YAML, run `udisplay-gen build --lang micropython`,
copy a `.py` file to the device with Thonny or `mpremote`, done — no toolchain,
no compiler, no flashing a whole firmware image. That's the actual on-ramp for the
Arduino/CircuitPython hobbyist crowd this project has never been able to reach
before, and it's the same "REPL and go" workflow that made MicroPython popular
in the first place.

## Constraints

- Must support MicroPython on ESP8266 and ESP32 at minimum.
- Generated code must also run unmodified on desktop CPython (mirrors demo01-03's
  existing "simulate on desktop" pattern for demo04).
- ESP8266 target has a concrete, repo-committed budget: full protocol + UI within
  80KB usable RAM (`demos/demo06/README.md`).
- Must reuse the existing `BuildContext` / `_BACKENDS` dict codegen architecture
  (`udisplay-gen/udisplay_gen/backends/`), not invent a parallel pipeline.

## Premises

1. This is a **pure-Python reimplementation** of `libudisplay`'s protocol layer
   (framing, chunked/merkle-verified blob transfer, heartbeat watchdog, optional
   HMAC auth) — not a native C-extension wrapper around the existing C code.
   Corrected reasoning (see Cross-Model Perspective — the original "impossible on
   ESP8266" justification was wrong): a native `.mpy` module can technically load
   on ESP8266's xtensa target, but (a) CPython can never load a MicroPython-compiled
   native module, so it can't satisfy the "must also run on desktop CPython"
   requirement anyway, and (b) native `.mpy` files are pinned to a specific
   mpy-cross/firmware ABI version and target architecture, meaning udisplay-gen
   would need to ship and maintain prebuilt binaries per (ESP8266 xtensa / ESP32
   xtensawin / ESP32-C3 rv32imc / firmware version) combination instead of one
   portable `.py` file. Pure Python wins on portability and distribution
   simplicity, not on native-module impossibility.
2. The ESP8266 target is bound by a concrete number the repo already committed to:
   80KB usable RAM for protocol + UI combined. Output-shape decisions get judged
   against that number with a stated fixture (widget count, blob size), not
   "ESP8266 in general."
3. Ships as a new `python_backend.py` alongside the existing c/cpp backends (same
   `BuildContext`/CLI pattern), plus a new pure-Python library module living inside
   `udisplay-gen` itself — not a separate repo — that the backend can either merge
   into generated output or reference as an import.
4. Distribution must be concrete per output mode — this directly gates `demo04`
   and `demo06`, both of which already carry placeholder READMEs with specific
   planned CLI usage (`udisplay-gen build x.yaml --lang micropython -o .`, then
   `micropython main.py` or `ampy put main.py`).

**Rejected approach, one line:** native C-extension wrapper around existing
`libudisplay.c`, considered and dropped — technically loadable on ESP8266's
xtensa target via native `.mpy`, but can't satisfy the "runs on desktop CPython
too" requirement and adds ABI/architecture-pinned binary distribution burden that
one portable `.py` file avoids entirely.

## Cross-Model Perspective

Independent Codex cold-read (context only, no conversation history):

- **Steelman:** "A YAML-to-Python toolchain that gives MicroPython developers
  named widget setters and callbacks, with the same generated application code
  runnable on CPython. One tested protocol runtime supports standalone files or
  shared-library deployments, while keeping memory use predictable on ESP8266."
- **Most revealing constraint:** the 80KB RAM number — "That makes peak memory,
  not resemblance to the C++ class hierarchy, the architectural driver... an
  unlimited UI cannot have a fixed RAM guarantee," i.e. the budget needs a stated
  fixture (widget count, blob size) to mean anything.
- **Challenged premise:** flagged that premise #1's original "pure Python is the
  only possible architecture" claim was wrong — MicroPython's native-module docs
  do list ESP8266's xtensa architecture as supported. Verified directly against
  `docs.micropython.org/en/latest/develop/natmod.html` — Codex was right, the
  premise was revised (see Premises §1) rather than defended.
- **48-hour prototype suggestion:** ship the "shrunk" output mode first — a
  thin generated glue file importing one maintained `udisplay_runtime.py`
  library, as opposed to a monolithic single-file merge (see Approaches
  Considered below for the full definition). Protocol v0: sync
  callbacks, explicit `feed()`, TCP framing, handshake, chunked transfer with
  real Merkle verification, event dispatch, heartbeat/reconnect. Skip BLE, HMAC,
  and asyncio for v0. Validate the RAM budget by running the generated output on
  a Unix MicroPython build with a constrained heap, sweeping down from 80KB and
  instrumenting allocator peaks through cold import, init, max-size transfer, and
  reconnect — noting this proves a reproducible heap-budget result but can't
  certify real ESP8266 compliance (WiFi allocations, port config, fragmentation
  still need the demo06 hardware gate).

## Approaches Considered

### Approach A: Minimal viable — shrunk-only, TCP-first, no auth
`python_backend.py` emits only the shrunk mode (thin generated glue importing a
`udisplay_runtime.py` library). Protocol v0 = TCP transport, sync callbacks,
handshake + chunked/merkle transfer + heartbeat. BLE fragmentation and HMAC auth
explicitly deferred.
- Effort: M (revised up from an initial S/M pass — the real port surface is
  `udisplay.c` (410) + `protocol.c` (224) + `chunk_server.c` (41) +
  `framing.c`'s TCP-only half (~52 of its 195 lines; the rest is BLE
  fragmentation, out of scope for v0) = ~727 combined C lines, not the ~460
  implied by naming only 3 of the 4 files). Risk: Low-Med — mechanical port
  of a well-specified state machine, but two v0-blocking unknowns are still
  open (the RAM fixture, the device event-loop shape — see Open Questions),
  either of which could block ship. (A third unknown, SHA-256 module
  availability, was raised and then retracted during `/plan-eng-review`
  outside-voice — see Open Questions.)
- Fastest path to `demo04` going from Placeholder to Works; exercises the
  highest-risk boundary (generated code importing the shared library) on day
  one; matches Codex's independent recommendation.
- Doesn't deliver "one drop-in file" for the single-instance hobbyist use case
  first; BLE (the project's primary demoed transport) isn't validated first.

### Approach B: Ideal architecture — full 3-mode backend, protocol-complete from day one
`udisplay_runtime.py` ships full parity with `libudisplay.c` (BLE + TCP + merkle
+ heartbeat + HMAC auth) before any output mode ships, then all 3 output modes
(library-only, shrunk, monolithic merge) land together.
- Effort: L/XL. Risk: Med-High.
- Matches the original ask in one pass, symmetric with the existing c/cpp
  backends which both already support the full protocol.
- Longest stretch before anything is runnable; this repo has hit this exact
  failure shape twice already per its own logged learnings (WidgetDelegate
  top-level dispatch gap, dpad `childModel` wiring gap) — build the whole
  surface, test it later, find the gap after the fact.

### Approach C (rejected): retire "monolithic merge" as a udisplay-gen feature
Only ever ship the shrunk mode; "one file" users freeze both files into custom
firmware or `mip install` the library instead of udisplay-gen inventing
source-merging logic. Rejected because it directly contradicts the explicit
"no library requirement" ask for the monolithic case and reintroduces a
firmware-build step for the exact hobbyist persona this feature exists to
serve — the tradeoff wasn't worth the reduced codegen surface.

## Recommended Approach

**Approach A.** Fastest way to turn `demo04` from a placeholder into something
real, independently proposed by Codex, and it sequences the risky, unverified work
(BLE fragmentation and HMAC auth ported into pure Python) after the shared-library
import boundary has been proven end-to-end — rather than before, which is the
shape of two bugs already logged against this codebase.

## Open Questions

- Exact RAM fixture to validate against the 80KB budget: how many widgets, what
  blob size, is a "typical" demo06-shaped UI enough or does it need to be the
  worst case the schema allows (up to `MAX_WIDGETS` = 240, up to the 64-chunk
  blob-size ceiling in `_shared.py`)? The RAM Success Criterion below is
  blocked on this being pinned first.
- **RETRACTED (verified during `/plan-eng-review` outside-voice, 2026-09-11):**
  this session originally raised "SHA-256 availability" as a standalone v0
  risk, on the assumption the device needs to run Merkle chunk verification
  at runtime. Codex's outside-voice pass challenged this; I verified directly
  against `libudisplay/src/chunk_server.c`, `protocol.c`, and `udisplay.c` —
  **the device never calls a hash function at runtime.** It only serves
  `chunk_hashes[idx]`, pre-computed by `merkle.py` at *build time* (desktop
  CPython, already required today for all 3 backends). Verification of those
  hashes happens on the **client** (`udisplay-client`, already existing
  C++), not the device. `udisplay_runtime.py` needs zero cryptographic hash
  functions for v0 — this eliminates the SHA-256/`uhashlib` availability
  risk, the import-time fail-fast check, and the corrupted-chunk test from
  this design's scope entirely (see Test Plan). `uhashlib` only becomes
  relevant if/when the deferred HMAC-auth path lands — see the bullet below.
- No MicroPython firmware/version baseline is pinned yet, despite the doc
  otherwise citing precise numbers (80KB, 64 chunks, `MAX_WIDGETS`=240) —
  module availability (`usocket` vs `socket` naming, etc.) varies by version
  and needs a stated target.
- What the device-side event loop in the generated `main.py` actually looks
  like on ESP8266/ESP32 — blocking `socket.recv()` loop calling `feed()`, vs.
  a poll-based structure — is unspecified; needs a skeleton before codegen can
  emit it, mirroring the usage pattern already documented in `udisplay.h`'s
  header comment for the C API.
- Whether `udisplay_runtime.py` targets `uhashlib`/`hashlib` directly for the
  (currently deferred) HMAC-auth port, or stubs it out entirely until auth
  lands — affects the library's import-time footprint even when auth is unused.
- Where `python_backend.py`'s CLI surface lives: a new `--lang micropython`
  value on the existing `build` command (matches `c`/`cpp` precedent) vs. its
  own subcommand — recommend the former for consistency, but not yet confirmed.
- Once output modes beyond shrunk-only land (Approach B scope), what CLI flag
  selects among shrunk / monolithic-merge / library-only — not yet designed,
  out of scope for Approach A's v0.
- **Runtime API-version compatibility, directly relevant to the multi-instance
  use case.** Two separate YAML builds emitting into the same output
  directory (the exact multi-instance workflow you described: "Make steps
  are creating multiple shrunk files and one library") means a later build's
  `udisplay_runtime.py` can silently overwrite an earlier one beneath an
  already-generated glue file. If the runtime's API ever changes between
  those builds, the older glue file breaks against the newer runtime with no
  version check. Needs either an embedded version constant `glue.py` checks
  at import time, or an explicit "don't overwrite a newer runtime" build-time
  guard — not yet designed. (Cross-model finding, Codex outside-voice.)

## Success Criteria

- `python_backend.py` registered in `_BACKENDS` alongside `c`/`cpp`, generating
  a shrunk-mode glue file + `udisplay_runtime.py` from a YAML input.
- Generated output round-trips a real desktop-client TCP session: handshake,
  chunked UI transfer served correctly (the client verifies against the
  Merkle root — the device only serves pre-hashed chunks, see Data Flow), a
  button press event delivered to a Python callback, a state update sent
  back — matching what `demo01`-`demo03` already validate for C/C++.
- `demo04` moves from Placeholder to Works using this backend's output on
  desktop CPython.
- Golden-vector cross-check against the C implementation: `udisplay-gen/tests/test_vectors.py`
  already has a `TestMessageVectors` class validating HANDSHAKE/CHUNK_REQUEST/
  CHUNK_RESPONSE/EVENT_*/framing against `tests/protocol_vectors.json`, the
  same fixture already shared with `libudisplay`'s and `udisplay-client`'s own
  C/C++ tests. The new work here is wiring a Python **encoder** into that
  existing fixture, not building byte-level golden vectors from scratch.
- RAM budget validated on a constrained-heap Unix MicroPython run against a
  stated fixture (blocked on the Open Questions fixture decision above),
  understanding this is a proxy for, not a replacement for, real ESP8266
  hardware validation via `demo06`. Anticipate that a naive line-by-line C→Python
  port commonly costs 2-5x memory over the C original (`udisplay_t` is ~2-2.5KB
  in C, dominated by fixed buffers) — plan for pre-sized `bytearray`/`memoryview`
  reuse and avoiding per-message allocation churn as v0 work, not a
  post-hoc fix if the budget is missed.

  **Measured (2026-09-11), MicroPython 1.24.1 Unix port, built from source
  in this session, against `demo04.yaml`'s fixture (11 ID-bearing widgets,
  including a button+LED child and a button-group+3-items composite):**
  - Raw `.py` source (`ui.py` + `udisplay_runtime.py`, as `python_backend.py`
    generates today): minimum viable `-X heapsize` is **~67-68KB** — fails
    at 66K, succeeds at 68K. That leaves only ~12-13KB of headroom under
    the 80KB target on this fixture, on the Unix port specifically.
  - Precompiled `.mpy` bytecode (`mpy-cross ui.py -o ui.mpy`, same for the
    runtime — the "future optimization" already named in Distribution
    Plan): minimum viable heap drops to **~32-33KB** — roughly half.
    Confirms the dominant cost is on-the-fly *source compilation* at
    import time, not steady-state object footprint, exactly as flagged in
    Cross-Model Perspective above.
  - Steady-state footprint (post-bootstrap, via `gc.mem_alloc()`) is small
    and bounded: ~4KB for `UI()` construction, **no growth** across 200
    simulated event/send/heartbeat cycles — no leak in the runtime itself.
  - **This changes the risk picture for ESP8266 specifically:** ~67KB
    minimum (raw source) leaves little margin against the unix port's own
    baseline being a poor proxy for ESP8266's actual free heap (WiFi stack
    overhead, MicroPython port differences) — worth treating `.mpy`
    precompilation as a real ESP8266 mitigation to reach for early, not a
    someday nicety, if real hardware (`demo06`) shows the raw-source
    number doesn't leave enough margin. Not re-scoped into v0 based on
    this alone — this is Unix-port evidence, not hardware evidence — but
    the Distribution Plan's "future optimization" framing may prove too
    casual once `demo06` has real numbers.

## Test Plan (v0)

Traced against every planned `udisplay_runtime.py` codepath (`/plan-eng-review`,
2026-09-11). Each gap below is a required unit test, not a follow-up:

- `on_disconnect()` — bootstrap state resets correctly.
- Malformed / unknown message type fed to `udisplay_on_message()` — rejected
  without raising, matching the C dispatcher's behavior.
- All 5 event types through `dispatch_event()` (button, slider, toggle,
  text-submit, dropdown selection) — the golden-vector fixture covers message
  *bytes*; this covers the Python callback actually firing per type.
- **Heartbeat watchdog**: miss counting reaches `HB_MISS_MAX` (3) and
  triggers teardown/`on_comms_error`, both during bootstrap stalls and after
  the connection goes active. No test currently named for this path at all —
  a silent, un-torn-down connection is exactly the kind of failure a real
  device operator would only discover by noticing the UI stopped updating.
- `set_property` / `reset_property` senders — not just the one state-update
  sender the round-trip criterion covers.
- **TCP reassembly** (the pre-sized-buffer design from Next Steps): a partial
  frame followed by the rest arriving in a later `recv()`; the buffer at
  exact capacity (overflow-signal path); multiple complete frames delivered
  in a single `recv()` call (mirrors `tcp_rx_feed`'s drain-loop in C).
- **Chunk serving for an out-of-range index** (`chunk_server_header_response`'s
  `idx >= cs->chunk_count` guard) returns the error response, not a crash —
  this is the device's actual integrity-adjacent responsibility; verifying a
  chunk's *hash* is the client's job, not tested here (see Data Flow — the
  device never runs a hash function at runtime, corrected during outside-voice
  review).
- Reconnect after a dropped connection (heartbeat-triggered or
  network-triggered) — ties directly to the heartbeat watchdog test above;
  currently the closest thing to "a user flow" in this v0 and untested.

## Distribution Plan

- Primary path: `udisplay-gen build x.yaml --lang micropython -o .` emits the
  generated glue file + `udisplay_runtime.py` into the output directory: copy
  both to the device with Thonny, `mpremote cp`, or `ampy put` (matches the CLI
  usage already documented in `demos/demo04/README.md` and
  `demos/demo06/README.md`).
- Desktop iteration path: the same generated files run unmodified two ways —
  under the MicroPython Unix port (`micropython main.py`, matching the exact
  usage already documented in `demos/demo04/README.md`) or under plain CPython
  (`python3 main.py`, satisfying the "should work on python as well"
  requirement). Neither is a separate build; both are the same file.
- Freezing/`.mpy`-precompiling `udisplay_runtime.py` for flash-constrained
  builds is a valid future optimization but explicitly out of scope for v0 —
  plain `.py` files first.

## Next Steps

1. Scaffold `udisplay_gen/backends/python_backend.py` following the
   `cpp_backend.py`/`_shared.py` pattern (`BuildContext` in, list of generated
   files out), registered in `cli.py`'s `_BACKENDS` dict.
2. Port `libudisplay/src/udisplay.c` (connection lifecycle, `udisplay_on_message`
   dispatch, `dispatch_event`, heartbeat watchdog, `udisplay_send_*`/property
   senders — the largest single file, ~410 lines), plus `protocol.c`,
   `chunk_server.c`, and `framing.c`'s TCP path (BLE and HMAC auth deferred)
   into `udisplay_gen`'s new `udisplay_runtime.py`, using the C source as the
   reference spec — a ~727-line combined surface (see Approach A for the
   exact breakdown). Before/during the port, grep the C source for
   function-body `static` locals (not file-scope `static` helpers) — this
   exact bug class (hidden state surviving a singleton-to-multi-instance
   refactor, e.g. `fill_auth_salt()`'s salt counter) already bit this
   codebase once (2026-07-30). Currently clean across all 4 files as of this
   review, but a Python port re-deriving from a future C revision should
   re-check, not assume.
3. Port the TCP inbound reassembly as a pre-sized `bytearray`/`memoryview`
   with explicit overflow signaling, mirroring `tcp_rx_feed`'s fixed-buffer +
   `memmove`-style compaction shape (`framing.c:172-190`) — not unbounded
   `bytes` concatenation, which would silently drop the RAM-budget discipline
   the C version enforces. Port outbound `socket.send()` partial-write
   handling too (mirroring `framed_send_raw`'s C behavior) — the inbound
   reassembly problem has an outbound mirror on a slow/busy link that's easy
   to miss if only `recv()` gets attention.
4. Design the generated glue file's per-widget public API — named setters and
   callback registration mirroring `_SETTER_TYPES`/`_HANDLER_TYPES` in
   `_shared.py` — this is the actual "similar to the modern C++ output"
   surface a user writes against, not just internal plumbing. **Output
   ownership constraint:** generated code and user-editable code (callbacks,
   credentials, application logic) must live in separate files, mirroring
   the C/C++ pattern (generated header + hand-written `main.c`) — re-running
   `build` must never destroy a user's edits.
5. Wire a Python encoder into the existing `udisplay-gen/tests/test_vectors.py`
   `TestMessageVectors` fixture (`tests/protocol_vectors.json`, already shared
   with the C/C++ suites) rather than building new golden vectors from scratch.
6. Wire `demo04` to the new backend end-to-end, runnable both under the
   MicroPython Unix port and under CPython; move it from Placeholder to Works.
7. Pin a target MicroPython firmware/version baseline (module naming like
   `usocket` vs `socket` varies by version — `uhashlib` is no longer a v0
   concern; see Open Questions retraction).
8. Sketch the device-side event loop for `main.py` (blocking `socket.recv()`
   vs. poll-based) before finalizing codegen for the glue file.
9. Implement the Test Plan (v0) section above; decide whether the new
   backend's tests run under Unix MicroPython in CI, not just CPython/pytest
   — the whole point of this backend is MicroPython compatibility, so CI
   should exercise the interpreter that actually matters.
10. **Done for the Unix-port proxy (2026-09-11)** — validated against
    `demo04.yaml`'s fixture, see Success Criteria for the measured numbers
    (~67-68KB raw source / ~32-33KB precompiled `.mpy`, both well inside
    80KB, but raw source leaves thin margin). Still open: the *worst-case*
    fixture (up to `MAX_WIDGETS`=240) is unmeasured, and none of this
    substitutes for real ESP8266 hardware validation in `demo06` — the
    Unix port's baseline is not the same as ESP8266's actual free heap.

## NOT in Scope (v0)

- **BLE transport** — deferred until the TCP path (and the shared-library
  import boundary) is proven end-to-end. Sequencing rationale, not a
  capability cut.
- **HMAC-SHA256 auth** — deferred, and consistent with existing behavior:
  `_shared.py`'s `_config_fields()` already hardcodes `auth_algo=UDISPLAY_AUTH_NONE`
  for the C and C++ backends too (codegen has no auth story yet, TODO-033).
  The Python backend isn't regressing anything by matching that.
- **Monolithic-merge and library-only output modes** (Approach B scope) —
  only the shrunk mode ships in v0.
- **Native C-extension wrapper around libudisplay.c** — considered and
  rejected (see Premises, "Rejected approach").
- **Retiring the monolithic-merge feature entirely** (Approach C) —
  considered and rejected; contradicts the explicit "no library requirement"
  ask for that mode.
- **Freezing / `.mpy`-precompiling `udisplay_runtime.py`** for flash-constrained
  builds — a valid future optimization, explicitly deferred (Distribution Plan).
- **Real ESP8266/ESP32 hardware validation** — the Unix-MicroPython-heap RAM
  check is a proxy for v0; the actual hardware gate is `demo06`, out of scope
  for this design phase.

## What Already Exists

- `BuildContext` / `_BACKENDS` dict (`backends/__init__.py`, `cli.py`) —
  reused as-is, no new codegen scaffolding.
- `_shared.py`'s setter/handler tables, `_config_fields()`, namespace-prefix
  helpers, hex-blob helpers — reused as-is.
- `docs/merkle.md` (TODO-001, already ✅ DONE) — a written spec for exact
  byte layout, hash algorithm, chunk sizing, and padding rules, meant
  exactly for "both the Python codegen AND the Qt C++ client" to implement
  from. The design doc's port step now cites this ahead of reverse-engineering
  the C source (Step 0 finding).
- `udisplay-gen/tests/test_vectors.py`'s `TestMessageVectors` +
  `tests/protocol_vectors.json` — already a shared fixture across C and C++;
  extended, not rebuilt, for Python.
- `widget_ids.py` — single-sourced widget-ID assignment already consumed
  identically by all backends; the new Python backend introduces no
  duplicate derivation of this specific concern (contrast with the Merkle/
  heartbeat/framing logic, which genuinely is a new independent
  implementation — see TODOS proposal below).
